# Rillgate 开发方案

更新日期：2026-10-06

当前核心交付：`cloud.23`，运行源码 `623b46d4dff1242acd8334cc8ed30bc737d293e1`。准确源码的 6 项 CI、云端公司测试接口的官方 SDK 调用、页面操作和撤权验收通过；公开 Cloudflare MCP 在独立本地临时网关完成真实接入。完整范围见[发布证据](evidence/gateway-core-release-2026-10-06.json)。Cloudflare 生产出站变更尚待批准，当前 Microsoft Learn 会话绑定 schema 不兼容；真实供应商 OAuth 授权不计入本次已验收范围。

本方案定义后续开发顺序与验收重点。已有实现以 [实现状态](implementation-status.md) 为准；源码实现与上线验收分别记录，下面的实现状态不代表已经上线。产品与架构文档保留长期范围，近期优先级以本方案为准。

## 1 产品主线

**接入工具 → 授权给 Agent → Agent 搜索并调用**

Rillgate 将已有业务 API、原生 MCP 与内网工具集中接入，让多个 Agent 复用同一套工具目录、访问权限和运行记录。Gateway 独立于模型运行；用户使用已有 MCP 客户端。Pi 仅作为可选联调与端到端验证客户端，不是网关运行或验收的前置依赖。

参考 [Uber MCP Gateway](https://www.uber.com/jp/en/blog/designing-mcp-gateway/) 的统一入口、控制面与执行面、按需发现、响应投影和 Code Mode 思路。写操作独立审批与 UNKNOWN 核查属于本项目额外的治理设计。不会把每次调用人工审批作为所有场景的产品前提。

两条用户路径：

- 工具负责人：添加服务、配置认证、检查连接、审查并发布工具、分配访问权限。上线审查发生在工具配置变更时。
- Agent 开发者：取得客户端连接配置，搜索工具摘要，按需读取参数定义，调用并获取结果。运行时仅在工具策略要求时等待审批。

首个完整版本只交付网关核心。控制台围绕“服务与工具、访问密钥、调用记录”组织，审批等高级配置按需要展开；现有客户端记录代表机器身份与授权，不代表需要建设一个客户端软件。Agent 工作台与多 Agent 编排暂停扩展。

## 2 复用已有实现

复用现有 Go API/Gateway/Worker、PostgreSQL、React 管理控制台和出站 Connector。已有 Pi 代码保留兼容维护，后续不为任务工作台增加新的产品范围。继续复用连接诊断、凭证、目录版本、授权、操作记录、幂等和 UNKNOWN 处理。

按功能包完善现有接口和页面。无需为了调整产品重点重写底层架构，也无需要求业务用户理解内部状态机才能发起普通调用。

## 3 开发顺序与验收

每个功能包分别完成契约、实现、针对性测试与真实链路验证。每包包括错误、权限、撤权和兼容性检查；仅源码实现或合成测试通过不等于云端验收完成。

| 顺序 | 用户得到的能力 | 开发范围 | 验收证据 |
| --- | --- | --- | --- |
| 1 接入与首次调用 | 从服务地址到 Agent 的第一次成功调用 | 串联现有连接、发现、审查发布与客户端授权页面；提供可复制的 MCP 连接配置、最小客户端示例和明确的诊断错误；将真实 OAuth 供应商兼容验证作为独立接入项跟踪 | 新建客户端通过标准 MCP 接口调用已发布的只读工具；未授权工具不可见且不可调用；记录步骤数和首次调用耗时；真实 OAuth 验证单独标明供应商与支持范围 |
| 2 按需发现 | 工具多时仍能找到正确工具 | 增加服务过滤与可解释的相关性排序；先核实环境元数据契约再增加环境过滤；保留摘要与 schema 分离、分页和实时权限过滤 | 固定含至少 1000 个工具的目录与中英文查询集，对比现有子串匹配的相关工具命中率、延迟和上下文大小；同名、无结果、禁用及撤权用例通过 |
| 3 简化调用与策略 | 普通操作直接得到结果，需要审批时能明确继续 | 提供简洁的调用入口，在服务端封装准备与操作 ID 管理；新增按工具配置的审批策略；保留旧接口兼容、幂等、实时授权和 UNKNOWN 处理 | 标准客户端覆盖只读调用、明确获准免审批的写入、待审批后继续、重复请求、并发、撤权、策略收紧与中断；写入只用隔离测试目标，未完成真实业务写入验证时明确标注 |
| 4 结果处理 | 调用方只收到需要的数据，并能按需读取大结果 | 完善结构校验、响应投影、分页和大小限制；设计有权限与有效期的大结果引用及分页读取；使用已有 MCP 客户端验证 | 裁剪不破坏分页和契约；产物越权、撤权、过期及大小边界通过；对比完整结果与按需读取的上下文用量，不将裁剪宣称为减少上游传输 |
| 5 可靠性与业务证据 | 调用稳定性和收益可检查 | 分类错误、仅对符合条件的只读操作重试、上游熔断、调用 trace 与延迟/错误看板；补齐固定负载测试和业务任务评测 | 展示超时、限流、上游不可用和进程中断下的行为；公布环境、负载、p50/p95、错误率、任务完成率及上下文成本；未知写入不自动重放 |

首次调用以公开 MCP 和已授权的公司测试只读接口为真实目标，内网 HTTP/stdio 使用已有 Connector 验证路径。新的 OAuth 账号或真实写入目标需要具备相应接入条件；其未验证状态与已经验证的接入方式分开记录。

### 当前实现与验收边界

| 功能包 | 当前源码实现 | 验收结论与边界 |
| --- | --- | --- |
| 接入与首次调用 | 密钥连接配置、仅使用提供密钥的 MCP 连通与目录检查、首次调用指引 | 官方 SDK 的云端测试接口调用与独立公开服务调用均通过；真实 OAuth 供应商授权尚未验收 |
| 按需发现 | `server_id` 过滤、固定层级相关性排序、摘要中的匹配原因、排名游标 v2 | 准确源码 CI、云端服务过滤与固定评测通过；旧 v1 游标需重新搜索 |
| 简化调用 | `call_tool` 封装准备与执行；管理员可版本化配置 `required` / `none`，旧接口继续可用 | 迁移、云端审批后继续、幂等与隔离写入测试通过；已有写工具不会自动获得免审批 |
| 结果处理 | MCP 结构化结果按策略选择字段；显式启用限量、到期产物，`read_result` 分块读取 | 云端结果完整性与撤权通过；过期、配额和并发以真实 PostgreSQL/SDK 隔离测试验证 |
| 可靠性 | 仅 HTTP 只读 GET 的有限重试与进程内熔断，保留幂等账本和 UNKNOWN | 固定负载故障测试与实际只读业务链路通过；不扩展为通用 MCP 重放或生产性能 SLA |

[固定发现评测](discovery-evaluation.md)保留了 1000 个工具、8 个中英文查询和一个排序未命中的样本，不能据此宣称语义检索质量或生产吞吐。大结果仅限 MCP 的 object `structuredContent`：投影后的完整 envelope 上限 1 MiB，保留 60–86400 秒，每工作空间最多 100 MiB / 1000 份产物；普通 HTTP 结果、任意文件和模型摘要不包含在内。

## 4 审批策略的调整边界

**当前源码已支持工具审批策略；线上行为以实际部署源码为准。旧写工具和缺省写策略继续要求独立审批，只有管理员显式修改为 `none` 才允许免审批调用。**

- 将副作用分类与审批策略分开，写操作不会通过改成“只读”获得免审批资格。
- 既有写工具和旧快照缺失策略时按风险使用保守默认值：写入要求审批、只读免审批；非法非空策略拒绝放行。
- 只有具备策略管理权限的人才能显式发布免审批规则，并记录差异和审计。模型、调用参数和客户端都不能自行选择绕过审批。
- 所有调用仍校验身份、工具授权、参数、启用状态、容量和操作记录。审批策略不扩大访问权限。
- 执行前核验最新权限和策略。策略收紧或绑定参数/版本改变后，旧授权不能直接沿用；既有待审批操作保持原绑定，不因策略放宽自动执行。
- 写调用仍需要稳定的业务幂等键；不确定结果仍返回 UNKNOWN。统一调用入口返回操作 ID 和明确状态，不将等待审批或未知结果包装为成功。
- 策略契约、迁移/回滚条件和回归验证完成后才发布此变更。

## 5 暂缓扩展

独立客户端软件、内置聊天与 Agent 任务工作台扩展、多 Agent 编排、模型账号管理、独立 CLI 产品、企业 SSO/MFA、多组织，以及 gRPC/IDL 自动扫描、全量协议兼容和大规模高可用，不纳入首个网关核心版本。Code Mode 暂以外部客户端或最小调用示例验证，不独立建设客户端产品。已有能力保留维护，实际连接需求再驱动协议扩展。

现有备份、健康检查与恢复要求继续执行。单机、异机备份和外部告警尚未完备等限制仍需公开记录；本次排序不构成生产就绪声明。

## 6 项目展示与验收主线

演示一次完整过程：接入公开 MCP 和自有测试 API → 发布授权 → 外部 MCP 客户端按需发现并调用 → 查看返回内容与调用记录。补充一次需要审批的写操作和一次结果未知的故障场景，说明治理能力如何触发。

同时提供可复现的测试集，比较全量工具定义与按需发现、完整响应与投影/按需读取。报告成功率、上下文用量与耗时，并披露失败样本；没有测量前不宣称具体节省比例。

接下来的发布验收按同一条主线执行，记录实际源码、客户端、服务目标和允许的调用；云端验证结果由发布记录补充。

## 7 网关核心完成标准

核心完成以声明支持的接入方式为边界，不以实现所有协议或所有企业功能为条件：

- 远程 Streamable HTTP MCP、固定 JSON HTTP API、Connector 的内网 HTTP/隔离 stdio 均有明确配置说明、诊断及可复现验证；真实供应商兼容清单与合成测试结果分开。
- 用户使用现有标准 MCP 客户端，通过网关完成发现、schema 读取与真实工具调用，全程无需启动 Pi 或创建平台 Agent 任务。
- 工具审查发布、密钥授权与撤销、参数校验、限流、记录和异常处理形成完整流程；未授权工具不可见且不可调用。
- 结果裁剪、分页与大结果读取边界明确；调用记录能定位主体、工具版本、耗时、错误和不确定结果。
- 每个功能包覆盖成功、失败、权限及恢复场景。CI 对 `scripts/go-coverage-targets.json` 声明的 Go 文件逐文件要求语句覆盖率至少 90%，使用 `-coverpkg=./...` 汇总单测与集成执行覆盖；Go profile 不提供独立分支覆盖指标。前端纯 TypeScript 逻辑采用聚合行覆盖率至少 95%、分支和函数覆盖率至少 90% 的门槛；TSX 组件不包含在内，UI 交互单独验收，不用局部覆盖率代表全仓达标。
- 至少完成公开 MCP 与已授权测试 API 的外部客户端端到端验证，并记录固定负载下的延迟、错误率及已知限制。
- 网关部署、备份恢复及故障定位有可执行说明；单机交付不宣称高可用或完整灾备。

连接配置与检查已整合到密钥管理流程，服务于已有 MCP 客户端。当前核心运行源码的 CI、真实链路和云端发布验收已完成。供应商兼容、真实 OAuth 和生产出站变更保持独立状态，不能用本次核心完成代替这些接入项的验收。
